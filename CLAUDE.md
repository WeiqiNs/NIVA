# NIVA for agents

PEAR, the non-interactive verifiable aggregation protocol of "Non-Interactive Verifiable Aggregation" (PoPETs 2025),
in Rust, combining the fully linear PCPs of RustFLPCP with inner-product functional encryption. Clients encrypt
`input || proof`, a server checks each ciphertext through function keys for the proof's linear queries and adds the
valid ones, and an analyst decrypts only the sum. PEAR is generic over the `Ipfe` trait with two backends: CLT
(Castagnos, Laguillaumie, Tucker, Asiacrypt 2018) over class groups of imaginary quadratic fields, the default; and a
research-grade RLWE scheme after Bermudo Mera, Karmakar, Marc and Soleimanian (PKC 2022), whose security is heuristic
(parameters from the lattice estimator, no reduction to PEAR's privacy game). `README.md` is the user-facing overview.

## Commands

```bash
cargo fmt --all -- --check
cargo clippy --all --all-targets -- -D warnings
cargo clippy --all --all-targets --features parallel -- -D warnings
cargo test --all --features parallel -- --include-ignored
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps
cargo llvm-cov --all --fail-uncovered-lines 0
cargo bench --bench pear -- --test '/10$'
cargo run --example quickstart && cargo run --example costs
cargo deny check && cargo machete
```

CI (`.github/workflows/ci.yml`) runs these on pushes, pull requests and a weekly schedule, in three jobs on the latest
stable Rust: lint, the test suite with `--features parallel` including the ignored full-size tests, and docs; tests
under coverage, the benchmark smoke run (only the length-10 configurations of both backends) and both examples, then
an OIDC upload to Codecov; and the dependency audit. Clippy pedantic is on through `[lints]` in `Cargo.toml`, which
also declares the `asm` feature value that ark-ff's `MontConfig` derive emits for the multi-limb headroom field. The
coverage gate is `--fail-uncovered-lines 0`, reached by tests that take each branch. `[profile.dev.package."*"]`
compiles dependencies with `opt-level = 3`, because unoptimized big-integer arithmetic makes the test suite several
times slower. `cargo run --example costs` prints each rule's vector length, CLT ciphertext size, query count and the
lattice ciphertext and public-key sizes.

## Layout

- `src/ipfe.rs`: `Ipfe<F>`, implemented on each backend's `Params` with the backend's own error type, which PEAR
  converts into `PearError` through `From`, and `IpfePublicKey<F>`, which maps a public key back to its backend so
  `Client::new` infers it. `Ipfe::encrypt` checks the message length like the inherent `encrypt`, and
  `Server::aggregate` uses `Ipfe::encrypt_zeros`, which cannot mismatch (`backend_encryption_checks_the_dimension` in
  `tests/pear.rs`). `src/debug.rs`: `redacted`, the size-only `Debug` output of both backends' keys.
- `src/clt/params.rs`: `Params` (`generate`, `decode`, the `lift` of a field element to an integer), `HsmGroup` (the
  message subgroup F generated by f, `power_of_f`, `solve`, the generator of the hidden subgroup), and
  `class_number_bound`.
- `src/clt/mod.rs`: `setup`, `PublicKey`, `MasterSecretKey`, `DecryptionKey`, `FunctionKey`, `Ciphertext`, the
  constants `SECURITY_BITS` and `DISCRIMINANT_BITS`, and the `Ipfe` impl.
- `src/lattice/ring.rs`: `Ring`, a negacyclic NTT over one prime field (`forward`, `constant_term`).
- `src/lattice/params.rs`: `LatticeField` (sealed; `Headroom` and `RING_DIMENSION`), `Headroom150`, `Params` (`new`,
  `encode`, `decode` with the noise ceiling, `linear_combination`), and the two-limb `Residue` (an element of Z_q) and
  `Polynomial` (a ring element in evaluation form).
- `src/lattice/mod.rs`: `setup`, `PublicKey`, `MasterSecretKey`, `DecryptionKey`, `FunctionKey`, `Ciphertext`,
  `MAX_DIMENSION`, and the `Ipfe` impl.
- `src/pear/mod.rs`: `Analyst`, `Setup`, `VerificationKey`, `Client`, `Server`, `Contribution`, each generic over the
  backend `S` with `clt::Params<F>` as the default.
- `src/class_group/mod.rs`: `Form` and `ClassGroup` (reduction, NUCOMP composition and NUDUPL squaring sharing one
  `finish`, inverse, prime forms). `src/class_group/exp.rs`: `pow` (signed windows), `FixedBase`, `multi_exp`
  (Pippenger), all over one `bucket_product` and `signed_digits`.
- `src/number_theory.rs`: `kronecker` and `is_probable_prime`. `src/sampling.rs`: `uniform_below`, the exact
  integer-only `DiscreteGaussian` (Canonne, Kamath, Steinke 2020) and `centered_binomial`.
  `src/linear_algebra.rs`: `linearly_independent`, shared by both backends' `function_keys`.
- `src/error.rs`: `CltError`, `LatticeError`, `PearError`. `src/field.rs`: `Field128`.
- `tests/`: `clt.rs`, `lattice.rs`, `pear.rs` (generic over the backend), `field.rs`, with `tests/common` holding the
  seeded rng and test parameters of both backends. Tests that need crate internals live in each module's
  `#[cfg(test)]` block.
- `benches/pear.rs` (`bench_backend`, one `{backend}/{rule}` group per rule), `examples/quickstart.rs` (the README's
  example), `examples/costs.rs`.

## How it works

- `Params::generate` takes p = `F::MODULUS` and draws a prime q with p·q ≡ 3 (mod 4), Kronecker (p/q) = −1 and
  p·q of exactly `discriminant_bits` bits; the bit minimum `2·bits(p) + 3` forces q > 4p. Δ_K = −pq and the group
  is the class group of Δ_p = p²·Δ_K. The generator g_p is the first split prime form raised to 2p, held as a
  `FixedBase` table. The Gaussian widths are those of the paper's Appendix D, with s̃ an integer upper bound on
  (1/π)·ln|Δ_K|·√|Δ_K|.
- `clt::setup` draws signed Gaussian secrets s_i and publishes h_i = g_p^{s_i}. `PublicKey::encrypt` draws r and
  outputs ct0 = g_p^r and ct_i = f^{x_i}·h_i^r. `PublicKey::eval` computes ∏ ct_i^{y_i}·ct0^{−sk_y} with `multi_exp`,
  and `DecryptionKey::decrypt` unmasks each coordinate with a `FixedBase` table of ct0⁻¹.
- `Params::decode` squares the form, reads the discrete logarithm in F from the reduced form `[p², L·p, ·]`, and
  multiplies by 2⁻¹ mod p.
- The lattice backend works in R_q = Z_q[X]/(X^n + 1) with q = p·Δ, p = `F::MODULUS` and Δ the prime modulus of
  `F::Headroom`, so every value is a pair of residues, one per field, and ring elements are kept as negacyclic NTT
  evaluations. `lattice::setup` publishes one uniform A and P_i = A·s_i + e_i with centred-binomial s_i, e_i.
  `encrypt` draws r, f0 and f_i and outputs ct0 = A·r + f0 and c_i = constant term of P_i·r, plus f_i + Δ·x_i. A
  function key holds the centred lift ŷ of y and sk_y = Σ ŷ_i·s_i; `eval` computes Σ ŷ_i·c_i − constant term of
  ct0·sk_y, and `decrypt` does the same with each unit vector.
- `lattice::Params::decode` reads the noise e as the centred Δ-residue, rejects |e| > Δ/4 with
  `LatticeError::NoiseTooLarge`, and returns (v_p − e)·Δ⁻¹ mod p from the p-residue.
- `Analyst::setup` builds the `Flp`, runs the backend's setup at the FLP vector length, draws one query, issues a
  function key per linear query, and keeps the decryption key restricted to the payload prefix.
- `Client::encrypt` proves and encrypts `input || proof`. `Server::validate` evaluates every function key, adds each
  query's constant, runs `Flp::decide`, and keeps only ct0 and the payload coordinates. `Server::aggregate`
  adds the contributions to a fresh encryption of zeros under the payload key. `Analyst::decrypt` returns the
  payload sum.

## Using another circuit

Any `rust_flpcp::Circuit<F>` works: pass it to `Analyst::setup`, `Client::new` and `Server::new` with the payload
length, the prefix of the input the analyst may learn. `Client::new` rejects a circuit whose vector length differs
from the public key, and `Server::new` one whose vector length, query count, function-key dimension or input length
does not fit the keys (`PearError::CircuitMismatch`, `setup_errors` in `tests/pear.rs`).

## Design facts

- Δ_p has exactly one class of order 2, which a client can multiply into any coordinate or ct0. Squaring before
  `solve` removes it, so a tampered ciphertext decodes as the untampered one
  (`two_torsion_tampering_decodes_as_untampered` in `src/clt/mod.rs`).
- A CLT ct0 inconsistent with the coordinates makes `eval` and `decrypt` return `CltError::NotInSubgroup` and
  `validate` return `None` (`eval_rejects_inconsistent_randomness`, `validate_rejects_inconsistent_randomness`).
  Lattice ciphertexts carry no such check: one from another setup of the same ring dimension decodes to an arbitrary
  value about half the time and to `NoiseTooLarge` otherwise, and only `Flp::decide` rejects it. One from another
  ring dimension is rejected with `LatticeError::RingDimensionMismatch` (`foreign_ring_dimension_is_rejected`).
- A valid contribution keeps only ct0 and the payload, and the aggregate is re-randomised by a fresh encryption of
  zeros, which also covers zero contributions (`honest_clients_aggregate_and_invalid_clients_are_rejected`,
  `aggregate_of_no_contributions_decrypts_to_zero` in `tests/pear.rs`).
- `FunctionKey` stores the lift of y once, used by both the secret key and `eval` (canonical for CLT, centred for the
  lattice); `function_keys` rejects vectors that are linearly dependent over the field
  (`decrypt_and_eval_recover_plaintext_and_inner_products`, `dependent_function_vectors_rejected` in `tests/clt.rs`
  and `tests/lattice.rs`). The check only sees one batch, so `function_keys` consumes the `MasterSecretKey` and
  returns a `DecryptionKey` that cannot issue keys: keys for y and 2y from two batches would combine into a key for a
  0/1 vector no one authorised.
- `MasterSecretKey`, `DecryptionKey`, `FunctionKey` and `VerificationKey` print only their sizes under `Debug`, since
  the reused query and the key secrets would let invalid inputs pass (`secret_debug_output_is_redacted` in both
  backends, `verification_key_debug_is_redacted`). The lattice `PublicKey` and `Ciphertext` print only their sizes too,
  because a full print runs to gigabytes, and the public key holds its polynomials in an `Arc` so cloning it per role
  is cheap.
- Gaussian exponents are signed, and every exponentiation path handles zero and negative exponents
  (`secret_key_has_negative_exponents_and_round_trips`, `exponent_laws_hold_for_signed_exponents`,
  `fast_exponentiation_matches_reference`).
- `Field128` has p − 1 = 2^66 · 3 · 3491 · 440340496364689, and 7 is a generator (`field128_parameters`).
- The generation conditions on q are checked by `generated_parameters_satisfy_cl_conditions`.
- Because p divides q, Δ·⟨x, y⟩ over the integers equals Δ·(⟨x, y⟩ mod p) in Z_q, so decoding needs no CRT
  reconstruction: the Δ-residue is the noise and the p-residue gives the message. `lattice_parameters_hold` checks
  Δ (prime, 150 bits, 2-adicity and generator against the factorisation of Δ − 1) and that Δ/4 covers the worst-case
  noise of `MAX_DIMENSION` coordinates at `RING_DIMENSION`; `noise_matches_its_predicted_spread` checks the noise of
  both signs against its predicted standard deviation.
- All ring elements stay in evaluation form and only forward NTTs run: the constant term of a product is n⁻¹ times
  the sum of the pointwise products, over a coset domain twisted by a primitive 2n-th root
  (`negacyclic_constant_term_matches_schoolbook`).
- The Δ/4 ceiling makes `eval` reject a ciphertext whose noise was pushed past it, while the analyst still decrypts
  it; without the ceiling such noise decodes correctly and goes unnoticed (`eval_rejects_noise_above_the_ceiling`,
  `validate_rejects_noise_above_the_ceiling`). The ceiling narrows, but does not close, a client's ability to probe
  the reused query through its own noise; the backend assumes clients encrypt honestly.
- A lattice ciphertext keeps only the constant coefficient of each P_i·r term, a public post-processing, so it is
  n + ℓ elements of Z_q (`examples/costs.rs` prints the sizes).
- Each coordinate gets an independent secret s_i. Secrets sharing ring structure (rotations of one secret) would let
  a key for y yield keys for every negacyclic rotation of y, which decrypts x.
- Lattice aggregates decrypt within the ceiling because decryption uses unit keys (`add_is_homomorphic_with_wraparound`
  sums 64). `eval` is sized for one ciphertext: the headroom over the worst-case noise of a single evaluation at
  `MAX_DIMENSION` is under one bit (`lattice_parameters_hold`), so evaluating a long key on a sum of many ciphertexts
  can exceed the ceiling. PEAR only evaluates single ciphertexts.
- dashu-int stays inside `class_group`, `number_theory`, `sampling` and the private fields of `clt`, so no big-integer
  type appears in the public API and swapping the big-integer crate touches only those files.
- Tests and benches use `StdRng::seed_from_u64` because `ark_std::test_rng()` is not a `CryptoRng`; randomized APIs
  take `&mut (impl CryptoRng + RngCore)` from `ark_std::rand`, which is `rand` 0.8.
